Application design system

Focused workspace for document-heavy XBRL review.

A clean, minimal interface for extracting, locating, reviewing and editing financial statement data. The design prioritises the source document, the mTool destination and the reviewer’s next decision.

STATUS · PRODUCTIONPALETTE · BLACK / ORANGE / GREY / WHITEDIRECTION · A

Principles

These rules control composition. They are more important than any individual component treatment.

01
Show the work, not an explanation of the work.

Use current tasks, values, evidence and dependencies. Remove preambles that restate what the screen already shows.

02
Keep recorded evidence one click away.

When authoritative page evidence exists, link directly to that PDF page. Highlight the exact region only when coordinates exist. Without page evidence, show a non-interactive manual-verification state rather than an empty source control.

03
Mirror the destination.

Review values and notes in a layout that closely matches their mTool fields, order and period columns.

04
Use progressive disclosure.

Keep audit history, technical activity and secondary metadata available but collapsed until requested.

05
Flatten the interface.

Prefer whitespace and alignment. Do not place cards inside a larger panel or divide every region with a border.

06
Reserve orange for meaning.

Use orange for identity, active work, source emphasis and compact attention icons. Selected controls use quiet surfaces, readable text and weight instead of accent lines.

07
Make parallel work legible without inference.

Show each agent's authoritative role, status, task, timestamp and page activity. Show hierarchy, handoffs or waiting dependencies only when the event contract supplies those relationships.

08
Make editing direct.

Reviewers should edit the canonical value or note in place and understand where that change will land in mTool.

Surfaces and borders

The default composition is white and flat. Borders explain an actual boundary; they do not decorate every block.

Use

Whitespace, column alignment, one subtle sidebar surface, a divider between persistent panes, and a light row hover or selection.

Avoid

Cards inside panels, multiple background tints, full-width warning bands, coloured borders around routine information and repeated header rules. Do not use accent lines for hover, pressed, active or selected states.

Current event contractThe production roster consumes agent_id, role, task, status, semantic update, timestamp and optional page evidence. Document preparation appears first because every extraction workstream depends on its page map. Long-running page and formatting fan-outs expose a plain-language count in the run header. Live activity streamMerge current activity, tool actions and provider-returned reasoning into one flat chronological Live activity stream for every active workstream. Stack concise updates from oldest to newest with the newest update at the bottom, using no event cards, navigation buttons or nested activity panels. Follow new updates only while the operator remains at the bottom; preserve their position when they scroll up to inspect earlier work. Frame-batch rapid reasoning updates and label available summaries Provider reasoning. Never describe unavailable private chain-of-thought as exposed. Announce only semantic status or tool changes to assistive technology, not every reasoning token, and make all motion respect prefers-reduced-motion.

Figures

Match mTool row order and period columns. Let the reviewer edit canonical values in place. Selecting a row immediately updates the PDF evidence.

Notes

Keep the full note index persistently visible and searchable. Use one click to switch notes and jump the PDF. Show editing tools only when the editor has focus.

Attention and warnings

Prefer a small icon at the affected object. Explain the issue on hover, focus or selection. Use a banner only when the whole page is blocked, with one neutral boundary rather than a coloured or heavy side rail.

Run transitions

The same agent rows change state as work moves through the pipeline. Do not replace the screen with a separate progress narrative.

Responsive behaviour

Preserve task order when space becomes constrained. Do not simply shrink three desktop panes until the content is unreadable.

01
Large desktop: persistent navigation, working surface and PDF or agent detail pane remain visible.
02
Standard desktop: narrow secondary rails first; keep the editable mTool surface dominant.
03
Tablet: move PDF or agent detail below the primary surface while retaining one-click selection.
04
Mobile: convert persistent rails to compact horizontal navigation. Financial tables may scroll horizontally; labels and period headers remain visible.

Accessibility

Minimal interfaces still require visible state, keyboard access and complete labels.

✓
Every icon-only control has an accessible name and a visible tooltip on hover and keyboard focus.
✓
Colour never carries status alone. Pair the orange dot with Working or Needs attention.
✓
Focus rings are black or neutral and clearly visible. They do not introduce a second accent colour.
✓
Agent filters and run-detail navigation use correct button or tab semantics with keyboard movement.
✓
Live agent updates use a polite live region. Do not announce every token or raw tool event.
✓
Respect prefers-reduced-motion; replace pulsing indicators with a static orange dot.
