Application design system

Focused workspace for document-heavy XBRL review.

A clean, minimal interface for extracting, locating, reviewing and editing financial statement data. The design prioritises the source document, the mTool destination and the reviewer’s next decision.

Principles

These rules control composition. They are more important than any individual component treatment.

01
Show the work, not an explanation of the work.

Use current tasks, values, evidence and dependencies. Remove preambles that restate what the screen already shows.

02
Keep recorded evidence one click away.

When authoritative page evidence exists, link directly to that PDF page. Highlight the exact region only when coordinates exist. Without page evidence, show a non-interactive manual-verification state rather than an empty source control.

03
Mirror the destination.

Review values and notes in a layout that closely matches their mTool fields, order and period columns.

04
Use progressive disclosure.

Keep audit history, technical activity and secondary metadata available but collapsed until requested.

05
Flatten the interface.

In Notes review, use plain bold field headings above white note content. Empty fields stay compact. Keep coverage counts, review warnings, reasons and sub-note details in the source note inventory; do not repeat the checklist below the editor. Prefer whitespace and alignment. Do not place cards inside a larger panel or divide every region with a border.

06
Reserve orange for meaning.

Use orange for identity, active work, source emphasis and compact attention icons. Selected controls use quiet surfaces, readable text and weight instead of accent lines.

07
Make parallel work legible without inference.

Show each agent's authoritative role, status, task, timestamp and page activity. Show hierarchy, handoffs or waiting dependencies only when the event contract supplies those relationships.

08
Make editing direct.

Reviewers should edit the canonical value or note in place and understand where that change will land in mTool.

09
Show outcomes, not implementation details.

Translate internal agents, row identifiers, evidence strings and technical workflow names into concise user-facing states. Keep diagnostics available outside the normal workflow.

10
Reserve indicators for exceptions.

Do not label every field Review or every row Working. Mark only items that need attention, were materially changed by automation or cannot be verified. A completed run must not turn failed or stopped formatting into Complete; show formatting completion only for a pass that ran and succeeded. Saved formatting status uses the latest attempt for each sheet or part; a later whole-sheet retry replaces older parts, while other current failures remain visible. Retain prior attempts under Formatting calls.

Clarity and simplification

The interface is a professional review workspace, not a diagnostic dashboard. Every default element must help the operator understand location, attention or next action.

Default to the task

Show what the operator must inspect or decide now. Keep secondary audit and configuration information behind a clearly named disclosure or in Settings.

Do not expose the pipeline

Do not make users interpret agent architecture, database identity, provenance syntax or workbook coordinates to complete an ordinary review.

Layout, overflow and navigation

01
Align the page: title, tabs, content and footer share a deliberate left edge and spacing rhythm.
02
Protect the work surface: navigation, editable content and source panes scroll independently where needed and never overlap.
03
Prioritise table meaning: description columns receive more width and may wrap; numeric columns remain compact and aligned. Browse mode stays within its pane; edit mode may scroll horizontally.
04
Make long content reachable: long notes use an obvious internal vertical scroll and never hide the next field or its Edit and Copy controls.
05
Keep navigation available: page controls, tabs and current context remain visible while scrolling without covering content.
06
Preserve source context: selecting a field or source-note subheading immediately opens its cited PDF page. A sub-note opens its own page when known, using the parent note page only when its own page is unavailable. If it has several destinations, retain a link to each field and preserve the sub-note page when switching. Reselecting the same item returns to that page even after manual paging.

Language and states

Use short, stable states: Waiting, Working, Complete, Needs review, Failed and Stopped. Use one term for one state. Empty states are quiet and actionable. Errors summarise the outcome first and keep technical detail in Activity or a closed disclosure.

Five-second testA new operator should be able to identify where they are, what needs attention and the next available action within five seconds. If a sentence, badge, border, menu or panel does not materially help one of those decisions, remove it from the default view.

Writing and microcopy

Words are part of the interface. Name every title, label, option and button so clearly that no extra sentence is needed. Helper text is the exception, not the default.

Main copy carries the meaning

01
Labels name the thing in the operator’s words. Use the accounting terms reviewers already use (Filing standard, Amounts in, Reporting periods). Never show internal names, agent names, sheet codes or field keys in the default view.
02
Buttons say the outcome. Verb plus object: Prepare mTool draft, Save decision, Retry preparation. Never OK, Submit, Proceed or Continue on their own.
03
Options explain themselves. Put the meaning in the option label (Current and prior, Current only) instead of a sentence under the control. Longer detail may sit in the option’s hover text.
04
Titles say where you are, once. Never repeat the page title in the top bar, an eyebrow, a panel heading or a description.
05
One term per concept, everywhere. The same state, object or action keeps the same word on every page, in buttons, statuses, dialogs and Activity.
06
Plain, short and sentence case. Everyday words, digits for numbers, no exclamation marks, no “please”, no abbreviations operators would not use themselves (MFRS and RM are fine; CY, PY and statement codes are not).

When helper text is allowed

Allowed (one short line)Not allowed
A format or limit the operator must know before entering a value: Up to 50 MB each. Must start with https://.Restating the label or the control: “Choose the model used for new runs” under a field called Model.
A consequence that is not obvious and affects other people or cannot be undone: Shared by everyone. May contain financial content.Describing what the system does automatically or in the background: “Document preparation will suggest a denomination for you to confirm.”
An exception the operator must act on now: Not found in the document. Select the unit shown in the statements.Introductions and page purpose: “This page lets you…”, “Here you can…”.
A validation or save error, shown directly below the control it concerns.Reassurance, defaults and rationale: “You can change this later”, “Default: 600 seconds. Increase this for long filings…”, how a feature works internally.

Limits

At most one helper line per control, no longer than about 12 words, in 13 px secondary text directly below the control. A section heading has no description, or one short line when the section changes something for everyone. Never use a paragraph of helper text, a grey explanatory box or a sentence that repeats a status shown elsewhere. Detected or automatic values appear as a small tag beside the label (Detected RM), not as a sentence.

Fix the words first

If a control needs explaining, rename it, split it or turn its options into self-explaining choices. Add helper text only when the label cannot carry the meaning.

Do not explain the interface to the operator

Do not narrate background work, restate what a control does or describe the screen. Put rare detail in hover text, a closed disclosure or documentation.

Messages

Status, empty and error messages lead with the outcome, then the action, in one sentence each: Not found in the document. Select the unit shown in the statements. Technical detail stays in Activity or a closed disclosure.

Hidden-helper testRead the screen with all helper text hidden. If an operator can still act correctly, delete the helper text. If not, fix the title, label, option or button first, then add the smallest helper line the table above allows.

Surfaces and borders

The default composition is white and flat. Borders explain an actual boundary; they do not decorate every block.

Use

Whitespace, column alignment, one subtle sidebar surface, a divider between persistent panes, and a light row hover or selection.

Avoid

Cards inside panels, multiple background tints, full-width warning bands, coloured borders around routine information and repeated header rules. Do not use accent lines for hover, pressed, active or selected states.

Motion and feedback

Use brief motion to connect an action to its result. The interface stays readable and responsive throughout.

01
Controls: hover, focus and pressed feedback takes 100–140 ms. A pressed control settles by at most 1 px. Never move a whole card or table row for decoration.
02
Content: a newly opened page section or tab panel may fade in with a shift of no more than 4 px over 180 ms. Animate a loaded list or table once as a region, not every row.
03
Dialogs and disclosures: dialogs fade and scale from 97% over 140 ms; disclosure content reveals over 180 ms. Keep the control and its result in the same place.
04
Status: update text, numbers and warnings immediately. Animate only their arrival. Reserve repeating motion for an active wait, and stop it at success, failure or cancellation.
05
Reduced motion: respect prefers-reduced-motion for every interaction. Replace transitions and pulsing with immediate state changes; never delay focus, navigation or a result.

Preserve task order when space becomes constrained. Do not simply shrink three desktop panes until the content is unreadable.

01

02

03
Tablet: move PDF or agent detail below the primary surface while retaining one-click selection.
04
