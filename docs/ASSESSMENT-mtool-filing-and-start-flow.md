# Assessment: mTool filing completeness, SOCIE, and the extraction start flow

**Date:** 2026-08-25

**Branch:** `codex/mtool-socie-audit`

**Baseline:** `46f2a11`

**Scope:** Assessment followed by implementation in this worktree.

## Implementation status

The proposed architecture is now implemented. Canonical concepts persist
taxonomy semantic addresses in schema v40. Forward mTool fill includes
data-entry SOCIE facts, resolves them to exact cells, and reports coverage.
Reverse benchmark ingest uses the same resolver. Automated round trips cover
MFRS/MPERS and Company/Group generated SOCIE templates.

After rebasing onto `main`, the start screen keeps the current review-and-start
flow. Document scanning and page preparation run inside the extraction pipeline
after the operator starts the run. The earlier automatic pre-scan proposal
later in this assessment is retained as historical rationale, not implemented
status. The mTool modal presents Check run → Choose template → Review result,
auto-inspects the workbook and note placement, and moves manual settings under
Advanced filing options.

One external acceptance item remains: add genuine current mTool 2.2 fixtures
and record Windows Validate/Generate plus generated-instance inspection. Until
then, unknown 2.2 layouts are reported as candidates rather than verified.

## Conclusion

The app prepares an mTool workbook; it does not submit a filing. The semantic
SOCIE and reverse-ingest gaps identified in the baseline are implemented in
this worktree, but genuine mTool 2.2 Windows acceptance is still outstanding.
Until that evidence is recorded, describe unknown uploaded layouts as a
candidate preparation path rather than a verified complete filing path.

The baseline gaps before this implementation were:

1. SOCIE numeric facts are deliberately excluded in both directions.
2. Repeated row labels make 185 of 327 full SOFP writes ambiguous in the
   measured template. Those values are correctly refused, but they are not
   filed.
3. Numeric scale behaviour remains unconfirmed. The shipped translation is
   identity even when a run is denominated in thousands or millions.
4. Only one genuine mTool workbook layout has recorded acceptance. The real
   Group and MPERS layouts are not present in the repository.
5. The final machine-generated workbook has not completed the documented
   Windows acceptance run with instance-value inspection.
6. The current official SSM download is mTool 2.2. The repository has no
   checked-in mTool 2.2 workbook fixture or recorded 2.2 acceptance matrix.

Recommendation: treat the feature as a pilot or partial preparation aid until
the regulatory acceptance gates below are complete. Do not present a partial
workbook as “ready to file” merely because the preflight has no data-quality
blockers.

The right technical solution for SOCIE is not a SOCIE-only column special
case. Build one semantic template-map module that resolves a fact by taxonomy
concept, period, entity scope, and XBRL dimensions. Use that module for both
forward fill and reverse ingest. This also fixes the repeated-label limitation
on SOFP and SOPL.

The extraction-start recommendations later in this assessment were superseded
by the newer `main` workflow. Models, repeats, benchmark grading, and recovery
controls remain behind Advanced settings in the current review-and-start form.

## What the feature does today

The app does not file directly with SSM. It:

1. reads reviewed facts and notes from a completed extraction run;
2. asks the user for an empty Excel template generated by mTool;
3. patches values and note text into that workbook;
4. returns the workbook to the user;
5. leaves Validate, Generate XBRL, and submission to mTool and mPortal.

The product label should therefore describe “preparing” or “filling” an mTool
workbook, not completing a filing.

The current implementation has strong safety controls:

- the workbook patcher is one standard-library-only implementation;
- formula cells are not overwritten;
- machine-generated writes require exact label matches;
- preflight blocks unresolved data conflicts, open reviewer flags, and notes
  coverage problems unless an operator records an override reason;
- a complete report is shown before the workbook is released;
- degraded downloads require acknowledgement;
- every fill has a durable receipt with numeric and prose revision digests;
- uploaded templates and generated artifacts are bounded and short-lived.

Those controls reduce silent failure. They do not prove filing completeness.

## Baseline evidence that drove the implementation

### SOCIE was explicitly omitted

`mtool/exporter.py::build_fill_doc` increments
`excluded_matrix_socie` and skips any matrix or `MATRIX_CELL` fact.
`eval/mtool_ingest.py` has the matching `matrix_deferred` path.

This is visible in the modal and reports, so it is not silent. It still means
the generated workbook is incomplete when the run contains SOCIE.

### Label addressing is already a larger general limitation

The current numeric write identity is approximately:

```text
(sheet name, visible row label, period/entity column role)
```

That is not unique. The same labels occur once per asset class on SOFP
sub-sheets. The existing plan records 185 of 327 SOFP writes, or 56%, as
ambiguous and therefore not written.

The correct response is not looser matching. The repository already refuses
to guess. The missing part is a stable semantic row identity.

### Real-template evidence is incomplete

`mtool/known_templates.json` contains one entry with
`source: "ssm-mtool"`: an MFRS Company 2024 sample. The referenced binary is
not in the repository. Four column-detection tests skip when that fixture is
absent.

Generated SSM-linkbase templates cover the code paths, but they are not proof
of behaviour in a workbook freshly exported by the current mTool.

### The documented operator questions remain unanswered

The answer block for Addendum A in `docs/MTOOL-ZIP-RECON-BRIEF.md` is empty.
It still asks:

- whether generated XBRL carries the displayed or full monetary value;
- whether negative signs survive;
- whether formula totals recalculate correctly;
- how genuine MPERS and Group workbooks mark their columns;
- whether the taxonomy concept key exists on every fresh template.

### Current SSM material confirms dynamic SOCIE structure

SSM's preparer guidance shows that users can select which equity components
appear in SOCIE. The current user manual also describes a fixed taxonomy
element column and reporting columns that vary by Company/Group and current/
prior period. The resolver must therefore read the actual workbook. A hardcoded
component order would not be safe.

SSM currently publishes mTool 2.2. Its release notes state that older template
versions may open read-only after taxonomy changes. Template compatibility
must be explicit in preflight and receipts.

## Recommended SOCIE solution

### Reject these two shortcuts

#### Shortcut A: add `component` to the existing label write

Example:

```json
{
  "sheet": "SOCIE",
  "label": "Profit (loss)",
  "component": "Retained earnings",
  "column_role": "current_year"
}
```

This can make a controlled SOCIE fixture pass. It still relies on human labels,
does not solve repeated SOFP rows, and creates a second matching model for
reverse ingest.

#### Shortcut B: emit physical Excel cells from the canonical template

Example:

```json
{"sheet": "SOCIE", "cell": "H11", "value": 1000}
```

Our template coordinates are not the operator's mTool coordinates. Component
selection, Group layout, language, and mTool version can change the position.
Physical cells are suitable only after the uploaded workbook has been
inspected and resolved in the same request.

### Recommended design: a shared semantic template map

Define a module with this small interface:

```python
template_map = inspect_mtool_template(workbook, expected_filing_family)
plan = resolve_filing_intent(filing_intent, template_map)
facts = read_filing_facts(workbook, template_map)
```

The implementation may be complex. Callers should only need these three
operations.

#### Semantic fact address

Use a generic address instead of a SOCIE-specific component field:

```text
primary taxonomy concept
+ period (CY/PY)
+ entity scope (Company/Group)
+ sorted XBRL dimensions (axis/member pairs)
```

For a linear statement, the dimensions set may be empty. For SOCIE it carries
the equity-component member. If the recon shows another relevant axis, the
same structure can carry it without another interface change.

The exact source identifiers must come from the SSM taxonomy and the actual
mTool workbook markers. Do not use translated labels as identity.

#### Module responsibilities

`inspect_mtool_template` should:

- verify the workbook fingerprint and mTool/template version where available;
- read the taxonomy concept key from the template row;
- read `#PRIM#`, `#ENDT#`, `#DOM#`, and `#UNITSCALE#` markers;
- derive period and entity roles from dates and dimensions;
- derive each SOCIE component from its dimension member;
- detect duplicate semantic addresses;
- return coverage, compatibility, and ambiguity findings.

`resolve_filing_intent` should:

- map each canonical fact to exactly one uploaded-template cell;
- refuse zero or multiple targets;
- produce explicit resolved cell writes for `offline_fill.py`;
- preserve the semantic address in the report and receipt;
- report coverage by statement, period, and entity scope.

`read_filing_facts` should:

- read values through the same semantic map;
- produce the exact keys used by gold facts;
- eliminate the separate reverse-ingest matching implementation;
- retain unmatched and ambiguous rows as explicit report items.

`offline_fill.py` should remain standard-library-only and should continue to
perform targeted XML edits. It can consume the resolved physical cells. It
must not learn about the database or import repository modules.

### Canonical-model change

The current canonical model stores `matrix_col` and `matrix_col_label`, but the
stable taxonomy identity needed for mTool is not exposed as a first-class
fact address. After the recon identifies the exact key, preserve that source
taxonomy concept and the dimension member identity during template import.

Prefer a schema field or generated mapping with one owner. Do not reconstruct
the identifier independently in the exporter and eval ingest paths.

### Required reconnaissance before implementation

Obtain fresh workbooks from the current mTool for:

1. MFRS Company SOCIE;
2. MFRS Group SOCIE;
3. MPERS Company SOCIE;
4. MPERS Group SOCIE;
5. MPERS SoRE as a regression fixture for the existing linear path.

For each workbook capture:

- mTool version and taxonomy version;
- workbook fingerprint;
- sheet name and structural marker rows;
- row taxonomy keys;
- equity-component axes and members;
- current/prior and Company/Group representation;
- unit-scale markers;
- one dividend, profit, opening balance, and closing balance value;
- the matching facts and contexts in generated XBRL.

The workbook may be sanitized. If binaries cannot be committed, keep small
targeted XML fixtures plus the original fingerprint and an operator-held copy.

### SOCIE implementation phases

#### Phase 0: evidence and contract

- complete the reconnaissance above;
- record a versioned semantic-address contract;
- decide the scale manifest from generated XBRL evidence;
- add mTool 2.2 compatibility policy to preflight.

Exit criterion: every address dimension and scale/sign rule is evidenced.

#### Phase 1: shared semantic map for linear statements

- preserve the taxonomy key during canonical import;
- inspect real mTool row identities;
- resolve existing linear facts through the new map;
- prove the SOFP repeated-label writes become unique;
- keep the old label resolver only as an explicit compatibility fallback,
  never as an unattended path.

Exit criterion: full linear coverage has zero ambiguous semantic addresses on
the accepted fixtures.

#### Phase 2: SOCIE forward fill

- include writable `MATRIX_CELL` facts in filing intent;
- resolve the component dimension and period/scope;
- include matrix writes in preflight's written-key set;
- add statement-level coverage to the report and receipt;
- remove the modal's SOCIE exclusion only after acceptance.

Exit criterion: generated XBRL contains the expected value, period, scope, and
equity-component context for every fixture.

#### Phase 3: SOCIE reverse ingest

- read SOCIE through the same template map;
- round-trip a filled run into gold facts;
- remove `matrix_deferred` only when the positive coverage test exists;
- retain explicit unmatched/ambiguous reporting.

Exit criterion: forward fill followed by reverse ingest reproduces the same
gradeable `MATRIX_CELL` facts.

#### Phase 4: release acceptance

- open every generated workbook in current mTool;
- run Validate and Generate;
- inspect generated instance values and contexts;
- cover MFRS/MPERS and Company/Group;
- record template fingerprints, mTool version, translation manifest, and
  acceptance evidence.

Exit criterion: no excluded required statement, zero unresolved numeric writes,
and operator acceptance on the supported matrix.

## Filing-workbook UX recommendation

The current modal presents readiness, notes choices, styling choices, template
upload, notes preview, column mapping, exceptions, fill, acknowledgement, and
download in one surface. Some controls are useful only after the template has
been inspected. The user has to infer the sequence.

Use a five-step state model:

1. **Readiness** — show blockers and coverage. Provide links to resolve them.
2. **Template** — upload the empty workbook. Inspect it automatically.
3. **Exceptions** — show only unresolved compatibility, placement, or mapping
   decisions. Skip this step when clean.
4. **Generate** — show one summary and create the workbook.
5. **Report and download** — show written/expected coverage, then release the
   file.

Default decisions should not be controls in the common path:

- fill notes when the run contains notes;
- create missing note spots when supported;
- use styled notes;
- calculate column and component placement automatically;
- run notes preview automatically after upload.

Move “No styling” to a support-only diagnostic disclosure. Show column letters
only when semantic detection cannot resolve a template. A filing user should
normally review accounting outcomes, not Excel coordinates.

Until SOCIE is supported, use one of these honest product states:

- block complete-workbook generation when the run contains SOCIE; or
- offer a clearly named “Create partial workbook” action with a required
  acknowledgement that identifies every excluded statement.

Do not let the top-level readiness message say “ready to file” while a required
statement is excluded.

## Extraction start-flow assessment

### Current common-path load

Immediately after upload, with Advanced settings closed, the panel can show
approximately 26 controls:

- Advanced settings;
- two filing-standard buttons;
- two filing-level buttons;
- three denomination buttons;
- the pre-scan toggle and Scan button;
- five statement-format selectors;
- five statement checkboxes;
- five notes-template checkboxes;
- Start extraction.

Opening Advanced can add repeats, benchmark grading, scanned-PDF handling,
and up to ten model pickers. After a pre-scan, the notes inventory editor and
technical log can add more decisions.

The main sources of confusion are:

1. Statements are configured twice: once in “Statement format” and again in
   “Statements to extract”.
2. The page asks users to opt into a pre-scan and then click a second button to
   run it, even though the pre-scan is the mechanism that could remove manual
   choices.
3. SSM output templates are presented as user goals. “Notes to include” asks
   for five implementation categories instead of first asking whether the user
   wants statements only or the complete filing notes.
4. Denomination is a high-risk decision but has the same visual weight as
   ordinary preferences.
5. The page has no single summary of what will happen, what was detected, what
   still needs confirmation, expected duration, or which choices are defaults.
6. Advanced controls change cost and evaluation behaviour but share the same
   long form as accounting decisions.

### Recommended start experience

After upload, run the document pre-scan automatically when it is enabled by
the firm's settings. Then show one review card:

```text
Ready to review

Detected filing
MFRS · Group · figures shown in RM'000

Included
5 primary statements · all notes found in the document

Needs confirmation
Denomination: RM'000 — detected from page 8

[Change selection]                         [Start extraction]
```

The primary path should require action only for:

- a missing or low-confidence statement format;
- a denomination that is unknown or conflicts with the document;
- an uncertain filing standard or filing level;
- an explicit user decision to exclude material content.

“Change selection” should open one edit surface where each statement row
contains its checkbox and format together. Do not render a separate format
table.

Use two notes presets before individual templates:

- **Complete extraction** — primary statements and applicable notes;
- **Statements only** — no notes.

An “Edit note types” disclosure can expose the five MBRS note templates for
special cases.

Advanced settings should contain:

- model overrides;
- repeat count;
- benchmark grading;
- scanned-PDF recovery when automatic text inspection reports a problem;
- technical pre-scan log.

It should not contain a control required to understand why Start is disabled.

### Recommended run-setup module

The current `PreRunPanel` owns many independent state variables and constructs
the payload at the end. Create one pure run-setup module:

```typescript
deriveRunProposal(upload, firmDefaults, preScan, savedDraft): RunProposal
validateRunProposal(proposal): ProposalIssue[]
toRunConfig(proposal): RunConfigPayload
```

`RunProposal` should distinguish:

- detected values;
- firm defaults;
- saved user overrides;
- confirmed values;
- unresolved issues.

The UI then renders the proposal and issues. Tests use the same interface as
the screen. This concentrates precedence rules and prevents a saved draft,
pre-scan result, and later user edit from silently overwriting each other.
